# 设计模式辨析：容易混淆的模式对，一次讲清

> 配套模块：module-13-design-patterns。本文不是重复讲 23 个模式，而是专门回答一个高频困惑：
> **"这两个模式长得好像 / 效果差不多，到底有什么区别？"**
> 每个模式对按 4 个层面拆解：**一句话本质 → 为什么容易混 → 三个关键区别（判据） → 代码级差异 + 误用场景**。
> 文中示例均可在本模块对应 Demo 类中运行验证。

---

## 0. 快速总览：一句话判据表

| # | 模式对 | 一句话区分判据 |
|---|--------|---------------|
| 1 | 工厂方法 vs 抽象工厂 | 创建**一个产品**还是**一族产品**？抽象工厂的回答是"请给我一套配套的" |
| 2 | 建造者 vs 工厂 | 你是**直接要成品**，还是要**一步步组装**（还能校验/定制）？ |
| 3 | 原型 vs 建造者 | 你是**复制现有对象**，还是**从零拼装**？ |
| 4 | 单例 vs 享元 | 要的是**全局唯一**，还是**相同就共享**（可以有多个不同实例）？ |
| 5 | 适配器 vs 桥接 | 是要**改接口让两者能用**，还是**解耦两个独立变化的维度**？ |
| 6 | 适配器 vs 门面 | 是**一对一转接**，还是**一对多聚合简化**？ |
| 7 | 装饰器 vs 代理 | 是**给对象加功能**（透明增强），还是**控制对对象的访问**（替身把关）？ |
| 8 | 装饰器 vs 组合 | 是**一条链**（每个包一个），还是**一棵树**（一个容器多个子）？ |
| 9 | 代理 vs 门面 | 是**控制访问/延迟加载**，还是**简化调用入口**？ |
| 10 | 策略 vs 状态 | 是**客户端主动换算法**（策略之间无关联），还是**对象内部自动流转**（状态之间有转移关系）？ |
| 11 | 模板方法 vs 策略 | 是**继承固定骨架**（流程父类定死），还是**组合替换算法**（整个算法都可以换）？ |
| 12 | 策略 vs 命令 | 是**同一个动作换实现**，还是**把动作本身变成对象**（可排队、可撤销）？ |
| 13 | 观察者 vs 中介者 | 是**一对多广播**（主题不认识订阅者），还是**多对多收敛为多对一**（同事互相认识对方）？ |
| 14 | 观察者 vs 责任链 | 事件是**发给所有人**，还是**沿链传、直到有人处理**？ |
| 15 | 命令 vs 备忘录 | 撤销的是**"操作"**（重放/逆操作），还是**"状态"**（整份快照覆盖）？ |
| 16 | 责任链 vs 装饰器 | 链上处理器是**竞争关系**（一个处理完就停），还是**叠加关系**（每个都执行并包装）？ |
| 17 | 迭代器 vs 访问者 | 你要的是**"怎么遍历"**，还是**"遍历时做什么操作"**？ |
| 18 | 解释器 vs 组合 | 树的节点代表**语法规则**（可求值/可解析），还是**部分-整体结构**（可递归求和）？ |

## 第一部分：创建型辨析

### 1. 工厂方法 vs 抽象工厂

**一句话本质**
- 工厂方法：**一个工厂方法创建一个产品**。客户端说"给我一个订单"，具体是普通/秒杀/团购订单由子类工厂决定。
- 抽象工厂：**一个工厂创建一族配套产品**。客户端说"给我一套浅色主题"，按钮和输入框必须配套，不能混搭。

**为什么容易混**
两者都叫"工厂"，都是把 `new` 藏起来，代码结构几乎一样（都是接口 + 多个实现类）。很多教程把抽象工厂画成"多个工厂方法"，看起来更晕。

**三个关键区别**

| 判据 | 工厂方法 | 抽象工厂 |
|------|---------|---------|
| 创建的粒度 | 一个工厂 = 一种产品 | 一个工厂 = 一族产品（多个产品，且必须配套） |
| 工厂接口里方法的数量 | 通常 1 个创建方法 | 通常 ≥2 个创建方法（每个产品一个） |
| 新增一种产品 | 加一个具体工厂类即可 | 所有工厂类都要改（因为每个工厂都要产这个新品） |

**代码级差异**（对照 `FactoryMethodDemo` / `AbstractFactoryDemo`）

```java
// 工厂方法：接口只有一个 create 方法
interface OrderFactory { Order create(double amount); }
class FlashOrderFactory implements OrderFactory {
    public Order create(double amount) { return new FlashOrder(amount); }  // 只产一种
}

// 抽象工厂：接口有多个 create 方法，返回的产品必须配套
interface ThemeFactory {
    Button createButton();     // 浅色工厂产"浅色按钮"
    Input createInput();       // 浅色工厂产"浅色输入框"——同族配套
}
```

**误用场景**
- 产品之间**没有配套约束**却用抽象工厂 → 白白多了方法，直接用工厂方法更简单。
- 反例：`AbstractFactoryDemo` 里如果让深色工厂产浅色输入框，就破坏了"产品族一致性"——这正是抽象工厂存在的意义。

### 2. 建造者 vs 工厂方法/抽象工厂

**一句话本质**
- 工厂：**一步创建，直接给成品**。创建过程内部隐藏，客户端拿到的对象"开箱即用"。
- 建造者：**分步组装，最后 build()**。客户端能看到/控制每一步，build() 时还能统一校验。

**为什么容易混**
都是"创建对象"，都能把 `new` 藏起来。有的框架（如 Lombok @Builder）让"建造者"看起来像"工厂"。

**三个关键区别**

| 判据 | 工厂方法 | 建造者 |
|------|---------|--------|
| 创建过程 | 一步完成，客户端不可见 | 分步执行，客户端参与每一步 |
| 参数多少 | 适合参数少、必填多的对象 | 适合参数多、可选多、有默认值的对象 |
| 校验时机 | 构造器里校验 | build() 统一校验（可检查必填项、字段间约束） |
| 最终对象 | 可以可变也可以不可变 | 通常产出**不可变**对象（Builder 与对象分离） |

**代码级差异**（对照 `FactoryMethodDemo` / `BuilderDemo`）

```java
// 工厂：一步创建
Order order = new FlashOrderFactory().create(80);   // 一步到位

// 建造者：分步 + build 校验
HttpRequest request = HttpRequest.builder()
        .url("https://api.example.com")   // 一步
        .method("POST")                   // 一步
        .header("A", "b")                 // 一步
        .build();                         // 最后校验：url 必填，缺失抛异常
```

**误用场景**
- 参数只有两三个且全必填，却套 Builder → 过度设计，构造器更清晰。
- 需要"同一份配置不同组合"时用工厂 → 工厂不擅长"默认值 + 可选覆盖"，Builder 的链式默认值才是正解。

### 3. 原型 vs 建造者

**一句话本质**
- 原型：**复制现有对象**（clone）。前提是已经有一个"原型"实例。
- 建造者：**从零拼装**。不依赖已有实例。

**为什么容易混**
都能"得到一个新对象"，而且 `BuilderDemo` 里 record 的 `withPort(3306)`（拷贝修改）长得特别像原型。

**三个关键区别**

| 判据 | 原型 | 建造者 |
|------|------|--------|
| 起点 | 必须有一个**现成实例**（原型） | 从空 Builder 开始 |
| 核心操作 | clone()：复制 + 微调 | 逐字段设置 + build() |
| 效率/场景 | 创建代价高、配置复杂的对象，复制比重建快（如大文档、游戏单位） | 参数多、校验多的对象 |
| 独立性 | 克隆体与原对象**必须互不影响**（深拷贝问题） | 天然独立，无共享 |

**代码级差异**（对照 `PrototypeDemo` / `BuilderDemo`）

```java
// 原型：从"已有对象"复制
Drawing prototype = new Drawing("主图", shapes);
Drawing copy = prototype.clone();     // 复制，改 copy 不影响 prototype

// 建造者：从零拼装
HttpRequest r = HttpRequest.builder().url("...").method("GET").build();
```

**误用场景**
- 原型浅拷贝导致克隆体改共享集合、污染原对象 —— 这是 `PrototypeDemo` 特意演示的坑（`shapes`/`meta` 必须新建集合）。
- 想"复制但不想实现 Cloneable" → 用 record 的 withXxx（`BuilderDemo.Config.withPort`），本质是"以旧换新"的原型变体。

---

### 4. 单例 vs 享元

**一句话本质**
- 单例：**全局只有一个实例**（强调唯一性）。
- 享元：**相同的就共享**（强调复用），可以同时存在多个**不同**的实例。

**为什么容易混**
两者都"少创建对象"，代码里都看到"同一个对象被反复使用"。

**三个关键区别**

| 判据 | 单例 | 享元 |
|------|------|------|
| 实例数量 | 永远 1 个 | 多个（按内部状态分组，每组 1 个） |
| 区分依据 | 无（就一个） | 按**内部状态**区分（如字体、棋子颜色） |
| 管理方式 | 类自己保证唯一 | 工厂/池按 key 缓存复用 |
| 典型例子 | Spring 单例 Bean、Runtime | Integer.valueOf 缓存、字符串常量池、线程池 |

**代码级差异**（对照 `SingletonDemo` / `FlyweightDemo`）

```java
// 单例：永远同一个
Singleton s1 = Singleton.getInstance();
Singleton s2 = Singleton.getInstance();   // s1 == s2，只有一个

// 享元：相同内部状态的复用，不同内部状态的有多个
Font f1 = FontFactory.get("宋体", 12, "粗体");
Font f2 = FontFactory.get("宋体", 12, "粗体");   // f1 == f2（复用）
Font f3 = FontFactory.get("黑体", 12, "粗体");   // f3 != f1（内部状态不同，新实例）
```

**误用场景**
- 用单例实现"共享缓存" → 应该用享元（共享的是"键相同"的对象，不是"全局唯一"）。
- 用享元存可变外部状态 → 享元的内部状态必须不可变，否则一个线程改了就全乱了（`FlyweightDemo` 里坐标是外部传入的，不入缓存）。

## 第二部分：结构型辨析

### 5. 适配器 vs 桥接

**一句话本质**
- 适配器：**改接口**。两个东西**已经存在**，接口对不上，加个转接头让它们能用。
- 桥接：**解耦维度**。两个东西**都要独立变化**，用组合把"抽象"和"实现"拆开，避免类爆炸。

**为什么容易混**
结构图几乎一样：都是"一个类持有另一个类"，都叫"包装"。很多面试者背了图却说不清意图。

**三个关键区别**

| 判据 | 适配器 | 桥接 |
|------|--------|------|
| 动机 | 接口不兼容（被动补救） | 主动设计，让两个维度独立扩展 |
| 对象关系 | 适配器把**已有**被适配者转成目标接口 | 抽象**主动持有**实现引用，两者在**设计期**就分离 |
| 变化点 | 被适配者/目标接口不变，只加转接 | 抽象维度、实现维度**各自**扩展（形状+渲染器 = 2+2 个类而非 4 个） |
| 比喻 | 转接头（国标插座→欧标插头） | 形状 × 渲染引擎自由组合 |

**代码级差异**（对照 `AdapterDemo` / `BridgeDemo`）

```java
// 适配器：ChineseSocket 是"改不动"的既有类，加适配器转成 EuropeanPlug
EuropeanPlug plug = new SocketAdapter(new ChineseSocket());  // 转接

// 桥接：Shape（抽象）构造时注入 Renderer（实现），两者都是新设计的
Shape circle = new Circle(new VectorRenderer(), 5);          // 组合
Shape rect   = new Rectangle(new RasterRenderer(), 4, 6);    // 换实现
Shape c2     = new Circle(new RasterRenderer(), 3);          // 同形状换渲染器
```

**误用场景**
- 主动设计阶段发现"两个维度" → 用桥接；上线后发现"接口对不上" → 用适配器。**先设计用桥接，事后补救用适配器**，这个时间点是最大分水岭。
- 桥接的经典误用：把"换数据库"当适配器（DriverManager 其实是桥接：JDBC 抽象 + 各家 Driver 实现）。

---

### 6. 适配器 vs 门面

**一句话本质**
- 适配器：**一对一**，转换接口让两边能用。
- 门面：**一对多**，聚合整个子系统，给客户端一个简单入口。

**为什么容易混**
都能"包一层"，调用方都只见一个类。

**三个关键区别**

| 判据 | 适配器 | 门面 |
|------|--------|------|
| 对象数量 | 包装 1 个对象 | 聚合多个子系统（≥2） |
| 目标 | 接口转换（不改行为逻辑） | 简化调用（内部有完整业务流程） |
| 方向 | 双向都可能（把 A 适配成 B 或反之） | 单向（客户端 → 门面 → 子系统） |
| 例子 | 插座转接头、InputStreamReader | `FacadeDemo.OrderFacade`：库存+支付+物流一键下单 |

**代码级差异**（对照 `AdapterDemo` / `FacadeDemo`）

```java
// 适配器：一对一转接
EuropeanPlug plug = new SocketAdapter(new ChineseSocket());

// 门面：内部编排三个子系统，客户端一行调用
OrderFacade facade = new OrderFacade();
facade.placeOrder("SKU-001", 2, 99.5, "北京");  // 内部：校验库存→扣减→支付→发货
```

**误用场景**
- 门面里塞多个"接口转换"逻辑 → 门面职责应该是"编排流程"，转换交给适配器。
- 子系统只有一个类却用门面 → 那就是适配器/直接调用，不需要门面。

---

### 7. 装饰器 vs 代理（最高频混淆点）

**一句话本质**
- 装饰器：**加功能**。给对象叠加新行为（咖啡加奶加糖），调用方**无感知**，接口完全一致。
- 代理：**控制访问**。替身把关（权限校验、延迟加载、远程调用），调用方**知道**自己在用一个替身（可选）。

**为什么容易混**
结构图几乎一模一样：`A 持有 B，调用 B 的方法并在前后加逻辑`。代码上装饰器和静态代理可以写到"看起来完全相同"。

**三个关键区别**

| 判据 | 装饰器 | 代理 |
|------|--------|------|
| 意图 | 增强对象**本身的能力** | 控制对对象的**访问** |
| 对象生命周期 | 被装饰对象由装饰器**层层包裹**，可无限叠加、顺序可变 | 代理是**唯一入口**，通常只包一层 |
| 与目标的关系 | 接口与目标**完全一致**（透明，客户端不感知） | 可以**扩展/限制**目标（加权限、延迟、拦截），客户端感知替身 |
| 是否创建目标 | 目标由外部传入 | 代理**可以自己创建**目标（虚拟代理延迟创建） |
| 典型例子 | BufferedInputStream 包 FileInputStream | 权限代理、虚拟代理（懒加载大图）、Spring AOP |

**代码级差异**（对照 `DecoratorDemo` / `ProxyDemo`）

```java
// 装饰器：一层层包，顺序随意，重点是"叠加"功能
Coffee coffee = new Espresso();
coffee = new MilkDecorator(coffee);
coffee = new SugarDecorator(coffee);        // 还能继续包

// 代理：控制访问，重点是"把关"
UserService proxy = new AdminProxy(real, false);   // 非管理员
proxy.updateUser("1", "改名");   // SecurityException：被保护代理拦截
```

**一句话记忆**：装饰器说"我让你的咖啡更好喝"；代理说"我是你老板的秘书，先过我这一关"。

**误用场景**
- 想加"日志/缓存"却用静态代理 → 两者都行，但 Spring AOP（代理）更通用；想**叠加多个**增强（日志+加密+压缩）→ 装饰器链更自然。
- 代理里创建并管理目标生命周期（虚拟代理）→ 装饰器不适合干这个，装饰器的目标必须外部传入。

---

### 8. 装饰器 vs 组合

**一句话本质**
- 装饰器：**一条链**。每个装饰器只包**一个**对象，形成线性包装。
- 组合：**一棵树**。容器可以挂**多个**子节点（子节点还可以是容器），形成树形结构。

**为什么容易混**
都用了"接口一致 + 递归"的思想，类结构有相似处。

**三个关键区别**

| 判据 | 装饰器 | 组合 |
|------|--------|------|
| 结构 | 链（1 对 1 包裹） | 树（1 对多） |
| 子对象数量 | 永远 1 个（被装饰者） | 容器可有多个 children |
| 递归方向 | 一层层剥（cost 逐层累加） | 一棵树遍历（size 递归求和） |
| 目的 | 动态叠加功能 | 表达部分-整体关系（叶子=文件，容器=目录） |

**代码级差异**（对照 `DecoratorDemo` / `CompositeDemo`）

```java
// 装饰器：一条链，一个包一个
coffee = new MilkDecorator(new SugarDecorator(new Espresso()));  // 线性

// 组合：一棵树，一个容器多个孩子
DirectoryNode root = new DirectoryNode("root");
root.add(src);          // 目录
root.add(new FileNode("pom.xml", 128));  // 文件——多个孩子
src.add(new FileNode("Main.java", 1024));
```

**误用场景**
- 用装饰器表达树 → 装饰器只能链，表达不了"一个目录下多个文件"。
- 用组合做"叠加功能" → 组合的容器没有"增强行为"语义，硬加很别扭。

---

### 9. 代理 vs 门面

**一句话本质**
- 代理：**控制访问**（权限、延迟、远程、日志）。
- 门面：**简化入口**（把一堆子系统收拢成一个方法）。

**为什么容易混**
都能"包一层"，调用方都只跟一个对象打交道。

**三个关键区别**

| 判据 | 代理 | 门面 |
|------|------|------|
| 包裹对象数 | 1 个真实对象 | 多个子系统 |
| 核心行为 | 拦截/控制/延迟（前后插逻辑） | 编排/聚合（把流程串起来） |
| 接口 | 与目标接口一致（或扩展） | 全新简化接口，可完全不同 |
| 典型例子 | 懒加载图片、权限校验 | 一键下单、SDK 封装 |

**代码级差异**（对照 `ProxyDemo` / `FacadeDemo`）

```java
// 代理：和 UserService 同接口，只是把关
UserService proxy = new UserServiceLogProxy(real);
proxy.findUser("1001");   // 方法签名不变，前后加了日志

// 门面：全新接口 placeOrder，内部串起库存/支付/物流
facade.placeOrder("SKU-001", 2, 99.5, "北京");
```

## 第三部分：行为型辨析

### 10. 策略 vs 状态（最高频混淆点之二）

**一句话本质**
- 策略：**换算法**。客户端**主动**选择用哪种（微信/支付宝/信用卡），策略之间**没有关联**，随便换。
- 状态：**自动流转**。对象**内部**根据当前状态决定行为，状态之间有**转移关系**（待支付→已支付→已发货），由事件触发。

**为什么容易混**
两者结构图完全一样：`Context 持有接口，接口有多个实现，行为委托给实现`。代码上几乎可以互相抄。

**三个关键区别**

| 判据 | 策略 | 状态 |
|------|------|------|
| 谁决定用哪个 | **客户端** setStrategy() 主动换 | **对象自己**根据事件/条件流转，客户端只触发事件 |
| 实现之间关系 | 无关联，可任意替换 | 有关联：**转移表**定义谁可以到谁（非法转移要拦截） |
| 语义方向 | 横向：同一时刻一种算法 | 纵向：随时间演进，状态在变 |
| 典型例子 | 支付方式、排序算法、Comparator | 订单状态机、TCP 连接状态、电梯 |

**代码级差异**（对照 `StrategyDemo` / `StateDemo`）

```java
// 策略：客户端主动换，换完行为立即变，无约束
context.setStrategy(new WeChatPay());   // 想换就换
context.setStrategy(new AlipayPay());   // 微信->支付宝无任何限制

// 状态：客户端触发事件，状态自己决定去向，非法转移被拦截
order.pay();                            // PENDING -> PAID
order.ship();                           // PAID -> SHIPPED
order.ship();                           // 抛异常：SHIPPED 状态不能重复发货！
```

**一句话记忆**：策略是**换**（客户端说了算）；状态是**流**（状态机说了算）。

**误用场景**
- 状态之间有转移关系却用策略 → 状态"下一步能去哪"没地方管，非法流转会漏。
- 算法彼此独立却用状态 → 白白维护一张转移表，过度设计。

### 11. 模板方法 vs 策略

**一句话本质**
- 模板方法：**继承**固定骨架。父类把流程定死（final），子类只填可变步骤（brew/addCondiments），还能用钩子控制流程走向。
- 策略：**组合**整个算法。Context 持有策略对象，整个算法都能被替换。

**为什么容易混**
都能"改变行为"，都能实现"开闭原则"。

**三个关键区别**

| 判据 | 模板方法 | 策略 |
|------|---------|------|
| 实现手段 | 继承（子类覆写步骤） | 组合（注入策略对象） |
| 可变粒度 | 只变**步骤**，**流程骨架固定** | 整个**算法**可整体替换 |
| 流程控制 | 骨架在父类，子类改不了顺序；钩子可影响走向 | Context 只调 strategy，没有固定流程概念 |
| 典型例子 | 饮品制作、JdbcTemplate、JUnit setUp/tearDown | Comparator、支付、压缩格式 |

**代码级差异**（对照 `TemplateMethodDemo` / `StrategyDemo`）

```java
// 模板方法：流程父类定死（final make），子类只填 brew/addCondiments
class Coffee extends Beverage {
    protected String brew() { return "滤纸冲泡咖啡粉"; }   // 步骤可变
}
// make() 的"烧水→冲泡→倒杯→(钩子)加料"顺序，子类改不了

// 策略：整个算法换掉
context.setStrategy(new WeChatPay());   // 整个 pay 逻辑换掉
```

**一句话记忆**：模板方法是"**流程**固定，细节可变"；策略是"**整个算法**都可以换"。模板方法用**继承**锁骨架，策略用**组合**换实现。

### 12. 策略 vs 命令

**一句话本质**
- 策略：**同一个动作**的不同实现（都是"支付"，只是方式不同）。
- 命令：**把动作本身封装成对象**，支持排队、记录、撤销、宏命令。

**为什么容易混**
都能"把行为参数化"，都常见"一个接口多个实现"。

**三个关键区别**

| 判据 | 策略 | 命令 |
|------|------|------|
| 封装对象 | 算法（怎么算） | 请求/操作（做什么 + 怎么撤销） |
| 撤销/重做 | 不支持（换了就换了） | 核心能力（undo 栈） |
| 调用者角色 | Context 直接调策略 | Invoker（遥控器）不碰 Receiver（电灯），只按按钮 |
| 参数化能力 | 换算法 | 命令可作为对象传递/排队/记录日志（事务） |

**代码级差异**（对照 `StrategyDemo` / `CommandDemo`）

```java
// 策略：换的是"实现方式"，没有"撤销"概念
context.setStrategy(new WeChatPay());
context.pay(100);                        // 付了就付了

// 命令：封装"操作"，可入栈可撤销
remote.setCommand(new LightOnCommand(light));
remote.pressButton();                    // 执行：开灯
remote.pressUndo();                      // 撤销：关灯（命令知道怎么反做）
```

**一句话记忆**：策略关心"**用什么方式**做"；命令关心"**做了什么、怎么撤销**"。需要撤销/重做/宏命令时用命令，否则策略更轻。

### 13. 观察者 vs 中介者

**一句话本质**
- 观察者：**一对多广播**。主题不认识订阅者（只维护 List），状态变了群发通知。
- 中介者：**多对多收敛**。同事之间不互相引用，都只认识中介者，交互全部经中介者转发。

**为什么容易混**
都能"解耦对象间的通信"，EventBus（`MediatorDemo.SimpleEventBus`）看起来就是观察者。

**三个关键区别**

| 判据 | 观察者 | 中介者 |
|------|--------|--------|
| 关系形态 | 1 对多（一个主题 → N 个观察者） | 多对多（N 个同事互相通信，都经中介者） |
| 通信方向 | 单向：主题 → 观察者 | 双向：任意同事 → 中介者 → 其他同事 |
| 参与者认知 | 观察者不参与通信协调 | 同事**主动**通过中介者发消息，中介者决定转发给谁 |
| 典型例子 | 气象站推送、公众号订阅 | 聊天室、机场塔台、MVC Controller |

**代码级差异**（对照 `ObserverDemo` / `MediatorDemo`）

```java
// 观察者：主题单向广播，订阅者被动接收
station.register(app1);
station.register(app2);
station.setMeasurements(25.5f, 60);   // 广播给所有订阅者，订阅者无法"回复"

// 中介者：用户主动发，中介者决定发给谁（排除发送者）
alice.send("大家好");   // alice 只认识 room，不认识 bob/carol
// room 内部：filter(u -> u != from).forEach(u -> u.receive(...))
```

**一句话记忆**：观察者是"**喇叭**"（单向喊）；中介者是"**总机**"（双向转接）。

### 14. 观察者 vs 责任链

**一句话本质**
- 观察者：事件**广播给所有**订阅者。
- 责任链：请求**沿链传递，直到有人处理**（中断式）或所有人处理（全链式，但那是过滤器语义）。

**三个关键区别**

| 判据 | 观察者 | 责任链 |
|------|--------|--------|
| 接收者 | 所有订阅者都收到 | 通常**一个**处理器处理（中断式） |
| 顺序 | 无严格顺序（List 遍历） | 有明确顺序（链的先后） |
| 控制权 | 订阅者被动 | 每个处理器决定"处理 or 传给下一个" |
| 典型例子 | 推送通知 | 审批流、Servlet Filter |

**代码级差异**（对照 `ObserverDemo` / `ChainOfResponsibilityDemo`）

```java
// 观察者：群发
station.setMeasurements(...);  // app1、app2、screen 全都收到

// 责任链：逐个问，谁有权谁处理
chain.approve(500);    // 组长处理，链停止
chain.approve(500000); // 组长→经理→总监→CEO，最后 CEO 处理
```

### 15. 命令 vs 备忘录

**一句话本质**
- 命令：撤销**操作**（execute/undo 成对，undo 是"逆操作"）。
- 备忘录：恢复**状态**（save/restore 快照，restore 是"整份覆盖"）。

**为什么容易混**
都支持"撤销"，常常一起用（编辑器 Ctrl+Z 既记操作又存快照）。

**三个关键区别**

| 判据 | 命令 | 备忘录 |
|------|------|--------|
| 撤销的对象 | 操作（知道"刚才干了什么"及逆操作） | 状态（整份字段快照） |
| 存储内容 | 命令对象（含 receiver 引用 + 参数） | 状态数据（record 快照） |
| 组合关系 | 宏命令 = 命令列表 | 历史栈 = 快照列表 |
| 典型例子 | 遥控器撤销、事务日志 | 编辑器撤销、游戏存档 |

**代码级差异**（对照 `CommandDemo` / `MementoDemo`）

```java
// 命令：undo 是逆操作——关灯命令的 undo 是开灯
remote.pressUndo();   // history.pop().undo() -> light.on()（反做）

// 备忘录：restore 是整份覆盖——内容+光标一起恢复
editor.restore(history.pop());   // content 和 cursor 都回到快照时
```

**一句话记忆**：命令撤销是"**反着做一遍**"；备忘录是"**回到存档点**"。生产环境常组合：命令记录"做了什么"，备忘录存"当时状态"，实现多级撤销重做。

### 16. 责任链 vs 装饰器

**一句话本质**
- 责任链：处理器**竞争**——一个处理完就停（审批），或层层过滤后放行（Filter）。
- 装饰器：装饰器**叠加**——每个都执行并**增强**，结果一层层包装。

**为什么容易混**
都是"链式结构"，都是"一个对象持有下一个"。

**三个关键区别**

| 判据 | 责任链 | 装饰器 |
|------|--------|--------|
| 处理语义 | 竞争/过滤：可能**中断** | 叠加：**每个都执行** |
| 调用方式 | 请求对象沿链传递 | 方法调用沿包装链递归（结果逐层加工） |
| 是否改变结果 | 通常不改变（谁处理给谁答复） | **改变结果**（cost 累加、description 拼接） |
| 典型例子 | 审批链、日志级别 | 咖啡叠加、IO 流包装 |

**代码级差异**（对照 `ChainOfResponsibilityDemo` / `DecoratorDemo`）

```java
// 责任链：500 元组长就处理完，链停止
chain.approve(500);   // 组长审批通过，不传给经理

// 装饰器：层层都执行，价格累加
new WhippedCreamDecorator(new SugarDecorator(new MilkDecorator(new Espresso())))
// cost = 15 + 3 + 2 + 5，description 全部拼接
```

**一句话记忆**：责任链是"**谁行谁上**"；装饰器是"**全都来一遍**"。

### 17. 迭代器 vs 访问者

**一句话本质**
- 迭代器：解决**"怎么遍历"**（顺序、逆序、跳过），把遍历逻辑从集合中抽出来。
- 访问者：解决**"遍历时做什么"**，把操作从元素中抽出来（面积计算、信息展示），元素结构不变却可加新操作。

**为什么容易混**
都跟"遍历"有关，都能"在不改集合的情况下扩展"。

**三个关键区别**

| 判据 | 迭代器 | 访问者 |
|------|--------|--------|
| 关注点 | 遍历**方式**（hasNext/next） | 遍历时的**操作**（visit 每个元素） |
| 谁来提供 | 迭代器提供访问序列 | 元素提供 accept(visitor)，visitor 提供 visit(元素) |
| 扩展方向 | 扩展遍历方式 | 扩展**操作**（加一个新 Visitor 就行） |
| 典型例子 | BookShelf 迭代、倒序迭代 | Shape 的面积/信息访问者 |

**代码级差异**（对照 `IteratorDemo` / `VisitorDemo`）

```java
// 迭代器：控制"怎么走"
Iterator<Book> it = shelf.iterator();
while (it.hasNext()) { Book b = it.next(); ... }   // 只负责取

// 访问者：元素把"自己"交给访问者，访问者决定做什么
circle.accept(areaVisitor);    // -> areaVisitor.visit(circle)
circle.accept(infoVisitor);    // 同一个元素，不同访问者做不同事
```

**一句话记忆**：迭代器是"**导游带路**"；访问者是"**检查团到访**"（每个元素接待，检查团成员各查各的）。

### 18. 解释器 vs 组合

**一句话本质**
- 解释器：树的节点是**语法规则**（表达式、操作符、数字），对树求值得到结果。
- 组合：树的节点是**部分-整体结构**（文件/目录），对树递归求和得到总量。

**为什么容易混**
解释器的抽象语法树（AST）和组合的对象树**结构长得一模一样**，都是递归树。

**三个关键区别**

| 判据 | 解释器 | 组合 |
|------|--------|------|
| 节点含义 | 语法规则（终结符=数字，非终结符=运算） | 业务对象（叶子=文件，容器=目录） |
| 核心操作 | **解释/求值**（interpret 返回结果） | **聚合/遍历**（size 递归求和） |
| 应用场景 | 表达式解析、规则引擎、正则 | 文件系统、菜单、UI 树 |
| 本质关系 | 组合是解释器的**结构基础**（解释器通常用组合构建 AST） | 组合本身无"语义计算" |

**代码级差异**（对照 `InterpreterDemo` / `CompositeDemo`）

```java
// 解释器：表达式树 -> 求值
Expression expr = new Add(new Number(1), new Multiply(new Number(2), new Number(3)));
expr.interpret();   // 1 + 2*3 = 7

// 组合：对象树 -> 递归求和
root.size();        // 所有文件大小之和，无"计算语义"，只是聚合
```

**一句话记忆**：解释器是**"会算的树"**（节点是规则，能求值）；组合是**"会装的树"**（节点是部分，能聚合）。解释器内部往往就是用组合来搭树的。

## 第四部分：终极三问（快速定位用哪个）

面试或写代码时，拿不准就按顺序问自己：

**第一问：你要解决"创建"问题吗？**
- 参数多、可选多、要校验 → **建造者**
- 已有实例、要复制 → **原型**
- 一个工厂一种产品 → **工厂方法**；一族配套产品 → **抽象工厂**
- 全局必须唯一 → **单例**；相同就共享 → **享元**

**第二问：你要解决"结构/接口"问题吗？**
- 接口对不上（补救）→ **适配器**；两个维度独立变化（设计）→ **桥接**
- 包一层加功能 → **装饰器**；包一层把关/延迟 → **代理**
- 聚合多个子系统给个简单入口 → **门面**；树形部分-整体 → **组合**

**第三问：你要解决"行为/协作"问题吗？**
- 客户端主动换算法 → **策略**；对象内部状态自动流转 → **状态**
- 流程固定细节可变 → **模板方法**；动作要可撤销/排队 → **命令**
- 状态要能恢复 → **备忘录**；一对多广播 → **观察者**
- 多对多收敛 → **中介者**；谁行谁上 → **责任链**
- 控制怎么遍历 → **迭代器**；遍历时做操作 → **访问者**
- 表达式规则求值 → **解释器**
