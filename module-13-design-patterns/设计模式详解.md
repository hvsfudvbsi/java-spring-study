# GoF 23 种设计模式详解

> 配套代码：`module-13-design-patterns/src/main/java/com/study/designpattern`。
> 本文不只给出一句定义，而是从**要解决的问题、结构角色、代码落点、适用边界和常见误用**逐个解释 23 种 GoF 模式。

## 0. 先理解：设计模式不是模板代码

设计模式是对重复出现的设计问题的经验总结，不是必须照抄的类图，也不是“用了接口就算用了模式”。判断一个模式是否合适，至少要回答三个问题：

1. 现在的代码痛点是什么：对象创建困难、接口不兼容、算法经常变化，还是对象之间耦合太重？
2. 哪一部分是稳定的，哪一部分是变化的？模式的价值通常是把变化隔离在一个边界内。
3. 引入模式后，新增需求是否更容易？如果类数量、跳转成本和抽象层次增加了，却没有带来可见收益，就是过度设计。

本模块的示例采用“常用写法 + 不常用写法”，不常用写法用于展示模式的变体、JDK 用法或函数式写法，不代表生产代码一定应该这样写。

# 一、创建型模式（Creational Patterns）

创建型模式关注“对象如何创建”。它们把 `new`、构造参数、初始化顺序、对象复用等变化隔离起来。

## 1. 单例模式（Singleton）

### 要解决的问题

某类在一个进程中应该只有一个实例，并且所有调用方都能获得它。例如配置中心、运行时环境、缓存管理器、线程池管理器。单例同时解决两件事：限制实例数量，以及提供统一访问入口。

### 结构与工作方式

典型单例包含：

- 私有构造器：阻止外部直接 `new`。
- 静态实例：保存唯一对象。
- 静态访问方法：返回实例。
- 并发控制：懒加载时需要保证多线程只创建一次。

常见实现有饿汉式、双重检查锁 DCL、静态内部类和枚举。Java 中推荐优先考虑枚举单例或静态内部类；DCL 必须配合 `volatile`，否则可能发生指令重排，其他线程拿到尚未完全初始化的对象。

### 代码落点

`creational/SingletonDemo` 展示了饿汉式、DCL、静态内部类、枚举单例，以及防反射/防序列化的加固方式。

### 优点与代价

优点是访问统一、实例数量可控、可以延迟初始化。代价是它引入全局状态，隐藏了依赖关系，测试时容易产生相互污染；多线程、类加载器、反射和序列化也会增加复杂度。

### 适用边界

只有当“业务上确实只能有一个”时才使用。需要共享的缓存、连接池或对象池，通常更接近享元或资源池，而不是单例。Spring Bean 默认单例并不等于所有业务对象都应该手写单例。

### 易错点

- 把工具类、无状态方法集合都写成单例：静态工具类或普通 Bean 更简单。
- 忘记处理序列化、反射或多类加载器场景。
- 单例持有可变状态，导致并发安全和测试隔离问题。

## 2. 工厂方法模式（Factory Method）

### 要解决的问题

一个业务流程需要使用某种抽象产品，但具体产品类型会增加或变化。如果业务代码直接写 `new WordDocument()`、`new PdfDocument()`，创建逻辑就和业务流程耦合在一起。

### 结构与工作方式

工厂方法包含：

- 产品接口：定义客户端真正需要的能力。
- 具体产品：实现产品接口。
- 工厂接口或抽象工厂：声明创建方法。
- 具体工厂：决定创建哪一种具体产品。

客户端依赖产品接口和工厂接口，不依赖具体产品类。新增产品时，通常新增一个产品类和一个工厂类，而不修改原有业务流程。

### 代码落点

`creational/FactoryMethodDemo` 中 `Document` 是产品接口，`WordDocument`/`PdfDocument` 是具体产品，`DocumentFactory` 是工厂接口，`WordFactory`/`PdfFactory` 是具体工厂。

同文件还展示了 Supplier 注册表和反射工厂。注册表适合插件数量较多且创建逻辑简单的场景；反射工厂灵活但失去编译期类型检查，异常也更晚暴露。

### 优点与代价

优点是隔离创建逻辑，符合开闭原则，便于替换产品和测试。代价是每增加一种产品可能增加一个工厂类，类数量会增长；如果产品只有一两种且不会变化，简单工厂或直接构造更清晰。

### 与抽象工厂的区别

工厂方法通常解决“创建一种产品”的变化；抽象工厂解决“创建一组必须配套的产品”的变化。判断关键不是看类图，而是看产品之间是否存在产品族约束。

## 3. 抽象工厂模式（Abstract Factory）

### 要解决的问题

系统需要创建多个相互关联的产品，并且这些产品必须来自同一个产品族。例如浅色主题必须同时创建浅色按钮和浅色输入框，不能出现浅色按钮搭配深色输入框的组合。

### 结构与工作方式

抽象工厂为每一类产品声明一个创建方法，例如 `createButton()` 和 `createTextField()`。每个具体工厂实现这些方法，并保证返回同一产品族的具体产品。客户端只依赖抽象工厂和抽象产品。

它最重要的不是隐藏 `new`，而是保证**族内一致性**。当新增一个主题时，新增一个具体工厂即可；当新增一种产品维度时，所有具体工厂都可能需要修改。

### 代码落点

`creational/AbstractFactoryDemo` 用浅色/深色主题表示产品族，用按钮/输入框表示产品维度。`LightThemeFactory` 永远创建浅色按钮和浅色输入框，`DarkThemeFactory` 永远创建深色产品。

### 优点与代价

优点是产品族约束集中在工厂中，客户端不会误组装；更换整套产品时只需替换工厂。代价是“新增产品种类”困难：所有工厂接口和实现都要增加方法。因此它适合产品族稳定、产品族之间变化较多的场景。

### 常见误用

如果产品之间没有配套关系，只是恰好都由一个类创建，就不需要抽象工厂。把所有创建方法都塞进一个“大工厂”会让接口膨胀，反而降低可维护性。

## 4. 建造者模式（Builder）

### 要解决的问题

对象构造参数很多，其中一部分可选，还有字段之间的约束。如果使用长参数构造器，调用方难以理解参数含义；如果使用多个构造器，会产生构造器重载爆炸。

### 结构与工作方式

Builder 把构建过程拆成多个可读步骤，最后由 `build()` 完成校验并创建对象：

```java
HttpRequest request = HttpRequest.builder()
        .url("https://example.com")
        .method("POST")
        .header("Content-Type", "application/json")
        .build();
```

Builder 可以保存默认值、检查必填字段、执行跨字段校验，并让最终对象保持不可变。复杂场景还可以把步骤设计成有顺序的接口，防止客户端跳过必要步骤。

### 代码落点

`creational/BuilderDemo` 中 `HttpRequest.Builder` 支持链式设置 URL、方法、请求头和超时，并在 `build()` 中检查 URL 和方法等必填条件。示例还展示了 record 的拷贝式 `withXxx` 与 JDK 的 `StringBuilder`/`Stream.builder()`。

### 优点与代价

优点是调用可读、对象可以不可变、校验集中、可选参数扩展成本低。代价是需要额外的 Builder 类型；参数少且简单时，Builder 会造成不必要的代码量。

### 与工厂的区别

工厂回答“应该创建哪个具体类型”；Builder 回答“如何一步步组装一个对象”。两者可以组合：工厂决定 Builder 或产品类型，Builder 负责细节配置。

## 5. 原型模式（Prototype）

### 要解决的问题

创建一个对象的成本很高，或者对象已经包含大量配置，重新调用构造器逐项配置很浪费。这时可以复制一个已有对象，再修改少量差异。

### 结构与工作方式

原型对象提供复制能力，客户端从已有实例复制出新实例。复制有浅拷贝和深拷贝之分：浅拷贝只复制引用，嵌套对象仍然共享；深拷贝需要复制可变集合和嵌套对象，确保副本修改不会污染原型。

Java 的 `Object.clone()`/`Cloneable` 是一种低层实现，但现代代码也常用复制构造器、静态 `copyOf` 或 record 的 with 方法来表达原型语义。

### 代码落点

`creational/PrototypeDemo` 展示图形的浅拷贝、带集合元数据的深拷贝、原型注册表和 record 替代方案。重点观察 `Drawing` 的元数据集合：只有复制集合，副本才真正独立。

### 优点与代价

优点是复制复杂对象时更快，能保留现有配置，适合对象模板和原型注册表。代价是复制语义容易出错，特别是引用字段、资源句柄、线程锁和外部连接不能简单复制。

### 适用边界

对象主要由数据组成、复制边界清晰时适合使用。包含数据库连接、线程、文件句柄或复杂生命周期的对象，不应直接 clone，而应重新构建或使用专门的复制方法。

# 二、结构型模式（Structural Patterns）

结构型模式关注“对象和类如何组合”。它们解决接口兼容、维度解耦、树形结构、功能叠加和访问控制问题。

## 6. 适配器模式（Adapter）

### 要解决的问题

客户端需要一个目标接口，但现有类已经有可复用的能力，只是方法名、参数或返回值不兼容。适配器不修改现有类，而是在两种接口之间做转换。

### 结构与工作方式

对象适配器通常包含一个被适配者引用，并实现客户端期望的目标接口：

```java
EuropeanPlug plug = new SocketAdapter(new ChineseSocket());
```

客户端只看到 `EuropeanPlug`，适配器内部负责调用 `ChineseSocket.supply220V()` 并转换语义。类适配器通过继承实现，但受 Java 单继承限制，通常优先使用对象适配器。

### 代码落点

`structural/AdapterDemo` 展示国标插座到欧标插头的对象适配器，也展示 `Arrays.asList`、`InputStreamReader`、`Collections.enumeration` 等 JDK 适配器。

### 优点与代价

优点是复用遗留代码、隔离第三方接口变化、客户端保持稳定。代价是多了一层转换；如果适配器承担了大量业务编排，就已经变成门面或服务层，职责不再单纯。

### 与桥接的区别

适配器通常是“已有接口不兼容后的补救”；桥接是在设计阶段就把两个独立变化的维度拆开。前者关注转换，后者关注解耦。

## 7. 桥接模式（Bridge）

### 要解决的问题

一个抽象维度和一个实现维度都可能独立扩展。若使用继承把它们排列组合，会产生类数量乘法增长，例如圆形/矩形 × 矢量/光栅需要多个组合类。

### 结构与工作方式

桥接把抽象和实现分别建模：抽象类持有实现接口，通过组合把实现注入进来。

```java
Shape circle = new Circle(new VectorRenderer(), 5);
Shape rect = new Rectangle(new RasterRenderer(), 4, 6);
```

新增一种形状只增加抽象侧类，新增一种渲染器只增加实现侧类，两侧可以独立演进。

### 代码落点

`structural/BridgeDemo` 把 `Shape` 与 `Renderer` 分成两个维度。`Circle`/`Rectangle` 是抽象侧，`VectorRenderer`/`RasterRenderer` 是实现侧。

### 优点与代价

优点是消除组合类爆炸，运行时可以切换实现，便于测试和扩展。代价是抽象层次变多，简单场景会显得复杂；如果两个维度实际上不会独立变化，直接继承或组合更直接。

### 常见应用

JDBC 把统一的数据库访问抽象与各厂商 Driver 分离，是桥接思想的典型例子。消息类型与发送渠道、UI 控件与渲染平台也常用桥接。

## 8. 组合模式（Composite）

### 要解决的问题

业务数据天然是树形结构，同时存在叶子节点和容器节点，客户端希望用统一方式处理两者。例如文件和目录、菜单项和子菜单、组织成员和部门。

### 结构与工作方式

组合模式定义统一组件接口：叶子实现具体操作，容器保存多个组件并递归调用子组件。这样客户端不需要反复判断“这是文件还是目录”。

```java
DirectoryNode root = new DirectoryNode("root");
root.add(new FileNode("pom.xml", 128));
root.add(srcDirectory);
long total = root.size();
```

### 代码落点

`structural/CompositeDemo` 中 `FileNode` 是叶子，`DirectoryNode` 是容器，两者都实现 `FileSystemNode`。目录的 `size()` 会递归汇总子节点，`flatten()` 会把树拍平成列表。

### 透明组合与安全组合

透明组合让叶子和容器拥有相同接口，客户端简单，但叶子可能被迫拥有 `add/remove` 等无意义方法。安全组合只在容器上提供子节点管理方法，类型更严谨，但客户端有时需要判断节点类型。

### 优点与代价

优点是树形递归逻辑统一，新增叶子或容器对客户端影响小。代价是“所有节点都支持哪些操作”需要权衡；复杂树还要考虑循环引用、深度过大和遍历性能。

## 9. 装饰器模式（Decorator）

### 要解决的问题

需要在不修改原类、不创建大量继承子类的情况下，为对象动态叠加功能，而且功能可以任意组合、调整顺序。

### 结构与工作方式

装饰器实现与被装饰对象相同的接口，同时持有一个同接口的委托对象。方法调用通常是“先调用委托，再加工结果”，多个装饰器可以形成链。

```java
Coffee coffee = new Espresso();
coffee = new MilkDecorator(coffee);
coffee = new SugarDecorator(coffee);
```

### 代码落点

`structural/DecoratorDemo` 用 `Coffee`、`MilkDecorator`、`SugarDecorator` 和 `WhippedCreamDecorator` 演示价格与描述逐层叠加；还展示 `BufferedInputStream`、同步 List 和函数式 Function 装饰。

### 优点与代价

优点是遵循开闭原则、组合灵活、每个增强职责单一。代价是对象层次变深，调试和类型判断变难；装饰顺序可能改变最终结果，必须明确组合规则。

### 与代理的区别

两者结构相似，但装饰器的核心是“增加能力并可多层叠加”，代理的核心是“控制访问、延迟创建、权限拦截或远程转发”。Spring AOP 通常基于代理，但多个业务增强也具有装饰器式叠加效果。

## 10. 外观模式（Facade）

### 要解决的问题

子系统内部有很多类和复杂调用顺序，客户端不应该了解所有细节。外观提供一个较高层、较稳定的入口，把复杂流程封装起来。

### 结构与工作方式

外观通常不改变子系统接口，而是组合多个子系统服务并编排流程。它可以做参数校验、调用顺序控制和结果统一，但不应把所有业务规则无限堆积到一个类中。

### 代码落点

`structural/FacadeDemo.OrderFacade` 将库存检查、库存扣减、支付和物流发货编排成 `placeOrder()`。客户端只需要调用一次，不需要知道子系统之间的顺序。

### 优点与代价

优点是降低客户端学习成本和耦合，适合作为 SDK、应用服务或模块边界。代价是外观可能变成“上帝类”；当外观暴露过多方法或承担大量领域决策时，应继续拆分应用服务和领域服务。

### 与适配器、中介者的区别

适配器是接口转换，通常包装一个对象；外观是流程聚合，通常协调多个子系统；中介者则处理多个同事对象之间的双向协作。

## 11. 享元模式（Flyweight）

### 要解决的问题

系统中存在大量相似对象，它们有一部分状态完全相同且可以共享。如果每个对象都保存一份相同数据，会造成内存浪费和创建成本增加。

### 结构与工作方式

享元把状态拆成：

- 内部状态：稳定、可共享、最好不可变，例如字体名称、字号、粗细。
- 外部状态：随场景变化、由调用方传入，例如棋盘坐标、文档中的位置。

享元工厂以内部状态为 key 缓存实例。相同 key 返回同一个对象，不同 key 返回不同享元。

### 代码落点

`structural/FlyweightDemo` 的棋子工厂按颜色和类型缓存棋子，坐标作为外部状态传入。`DocumentExportDemo` 中的 `FontFactory` 也展示了字体对象复用。

### 优点与代价

优点是显著降低大量重复对象的内存占用。代价是缓存管理、线程安全、对象生命周期和外部状态传递会增加复杂度；缓存无界还可能造成内存泄漏。

### 与单例、对象池的区别

单例强调全局唯一；享元按内部状态分组共享，允许多个实例；对象池管理的是可借用的资源，资源通常有使用中/空闲状态，语义不同。

## 12. 代理模式（Proxy）

### 要解决的问题

客户端需要访问某个对象，但访问前后需要加入权限、日志、缓存、延迟加载、远程调用或生命周期控制。代理提供与目标对象相近的入口，并决定是否、何时以及如何调用目标。

### 常见类型

- 静态代理：手写代理类，类型清晰但重复代码多。
- JDK 动态代理：基于接口和 `InvocationHandler` 运行时生成。
- 虚拟代理：真正使用时才创建重量级对象。
- 保护代理：根据权限决定是否放行。
- 远程代理：把本地调用转成远程请求。

### 代码落点

`structural/ProxyDemo` 展示日志静态代理、JDK 动态代理、延迟加载图片的虚拟代理和管理员权限代理。

### 优点与代价

优点是目标类无需修改即可增加横切逻辑，访问策略可以集中管理。代价是调用链变长，异常和事务边界可能被隐藏；JDK 动态代理要求接口，CGLIB 等类代理又有 final 方法等限制。

### Spring 中的联系

Spring AOP 的 `@Transactional`、缓存、权限和日志通常通过代理实现，所以只有从容器获取 Bean 并经过代理调用时，增强才会生效；同类内部 `this.method()` 不会重新经过代理。

# 三、行为型模式（Behavioral Patterns）

行为型模式关注“对象如何协作、职责如何分配、算法如何变化”。它们通常减少调用方与具体实现之间的耦合。

## 13. 责任链模式（Chain of Responsibility）

### 要解决的问题

一个请求可能由多个对象中的某一个处理，处理者的选择和顺序会变化。如果调用方写大量 `if/else` 或直接依赖所有处理者，就会与审批级别、过滤器顺序强耦合。

### 结构与工作方式

每个处理器保存下一个处理器，并决定：自己处理、拒绝，还是把请求传给下一个。责任链有两种语义：

- 中断式：一个处理器处理成功后停止，例如按金额审批。
- 全链式：每个处理器都执行，例如过滤器、拦截器、日志链。

### 代码落点

`behavioral/ChainOfResponsibilityDemo` 中 `TeamLeader -> Manager -> Director -> Ceo` 按金额传递，`approve()` 体现中断式责任链；`FunctionalChain` 用函数列表展示轻量变体。

### 优点与代价

优点是发送者不需要知道具体处理者，处理顺序可配置，新增处理级别不必修改客户端。代价是请求可能无人处理、链过长导致调试困难，顺序错误还可能产生安全问题。

### 与装饰器的区别

责任链中的处理者通常是竞争关系，目标是找到一个处理者或完成过滤；装饰器中的每一层都应执行，目标是叠加功能并加工结果。

## 14. 命令模式（Command）

### 要解决的问题

调用者只想触发一个动作，但不应该直接依赖接收者；同时还希望把请求排队、记录、重试、延迟执行或撤销。

### 结构与工作方式

命令对象封装：

- Receiver：真正完成工作的对象。
- Command：保存 Receiver 和参数，实现 `execute()`，通常还实现 `undo()`。
- Invoker：保存或触发命令，不需要知道 Receiver 细节。

命令对象可以像数据一样存入队列、历史栈或日志。

### 代码落点

`behavioral/CommandDemo` 用遥控器作为 Invoker，电灯作为 Receiver，开灯/关灯作为具体命令；`MacroCommand` 组合多个命令并按逆序撤销，`SimpleExecutor` 展示 Runnable 函数式命令。

### 优点与代价

优点是请求与执行者解耦，天然支持撤销、宏命令和排队。代价是每种操作可能都需要一个命令类；如果操作非常简单且不需要记录或撤销，直接调用更清晰。

### 与备忘录的区别

命令保存“做了什么以及如何反做”，备忘录保存“某个时间点的状态”。复杂编辑器常把两者组合起来：命令记录操作，备忘录提供可靠状态恢复。

## 15. 迭代器模式（Iterator）

### 要解决的问题

集合内部可能是数组、链表、树或数据库游标，但客户端只想顺序访问元素，不希望知道集合内部结构。迭代器把遍历算法从集合中分离出来。

### 结构与工作方式

迭代器通常提供 `hasNext()` 和 `next()`，集合提供 `iterator()`。不同迭代器可以实现正序、倒序、过滤、分页或深度优先遍历，而集合的存储结构不变。

### 代码落点

`behavioral/IteratorDemo` 让 `BookShelf` 实现 `Iterable<Book>`，支持 for-each、自定义倒序迭代器和迭代器转 Stream，还演示集合修改时的 fail-fast 行为。

### 优点与代价

优点是封装遍历细节、支持多种遍历方式、客户端依赖统一接口。代价是简单集合可能不需要自定义迭代器；并发修改、迭代器生命周期和懒加载异常需要明确约定。

### JDK 应用

`Iterable`、`Iterator`、`Spliterator` 和 Stream 都体现了迭代器思想。数据库 ResultSet、文件目录遍历和分页查询也可以把结果暴露成迭代器。

## 16. 中介者模式（Mediator）

### 要解决的问题

多个对象之间直接互相引用，形成网状依赖，任何一个对象变化都可能影响很多对象。中介者把多对多交互收敛为“同事对象 -> 中介者 -> 同事对象”。

### 结构与工作方式

同事对象只依赖中介者接口，发送事件或请求由中介者决定转发给谁、是否过滤、是否改变消息。中介者承载交互规则，减少同事之间的直接耦合。

### 代码落点

`behavioral/MediatorDemo` 中用户只认识 `ChatMediator`，不直接持有其他用户；`ChatRoom` 负责把消息转发给除发送者外的成员。`SimpleEventBus` 展示按事件类型注册消费者的函数式变体。

### 优点与代价

优点是把复杂协作集中管理，参与者变简单，新增参与者通常不需要修改所有旧参与者。代价是中介者可能膨胀成“上帝对象”，因此应按业务领域拆分多个中介者或事件通道。

### 与观察者的区别

观察者重点是主题向多个订阅者广播，订阅者通常被动接收；中介者重点是多个同事之间的协商、路由和双向交互。

## 17. 备忘录模式（Memento）

### 要解决的问题

对象需要支持撤销、回滚、存档或恢复，但又不希望管理者直接暴露对象内部字段。备忘录把对象某个时刻的内部状态封装成快照。

### 结构与工作方式

- Originator：创建和恢复快照的对象。
- Memento：保存状态的数据对象，通常不可变且对外只读。
- Caretaker：保存快照历史，但不应该修改快照内部。

快照可以放入栈实现撤销，也可以带版本号、时间戳和用户信息实现审计或历史浏览。

### 代码落点

`behavioral/MementoDemo` 用编辑器保存文本与光标状态，通过历史栈恢复；`ApprovalWorkflowDemo` 用 record `Snapshot` 保存审批状态和审批人。

### 优点与代价

优点是封装状态、恢复可靠、管理者不需要知道内部字段。代价是快照可能占用大量内存，频繁复制大对象需要增量快照、压缩或持久化；恢复时还要考虑版本兼容。

### 与命令的区别

命令撤销依赖逆操作，适合可逆且粒度明确的动作；备忘录直接恢复完整状态，适合复杂对象或逆操作难以可靠实现的场景。

## 18. 观察者模式（Observer）

### 要解决的问题

一个对象状态变化时，需要通知多个依赖者，但主题不应该硬编码每个依赖者。观察者模式建立主题和观察者的一对多关系。

### 结构与工作方式

主题维护观察者列表，提供注册、取消注册和通知操作。通知模型有：

- 推模型：主题把变化数据直接推给观察者。
- 拉模型：主题只通知发生变化，观察者再主动读取数据。

实际系统还要考虑通知顺序、异常隔离、同步/异步、重复订阅和观察者生命周期。

### 代码落点

`behavioral/ObserverDemo` 中 `WeatherStation` 是主题，`PhoneApp` 和 `DisplayScreen` 是观察者；`MessageCenter` 展示用 `Consumer<String>` 作为函数式订阅回调。

### 优点与代价

优点是主题与观察者解耦，新增订阅者不需要修改主题。代价是通知链可能难以追踪，观察者异常可能影响发布者，忘记取消订阅还可能造成内存泄漏。

### Spring 中的应用

Spring 的应用事件与 `@EventListener`、消息队列消费者、响应式流订阅都体现了观察者思想。跨进程场景不能只依赖内存观察者，需要消息中间件或事件总线。

## 19. 状态模式（State）

### 要解决的问题

对象在不同状态下行为完全不同，代码中出现大量基于状态的 `if/else`，并且状态之间存在合法流转关系。状态模式把每个状态的行为拆成独立对象。

### 结构与工作方式

Context 保存当前 State，把事件委托给当前状态。状态可以返回下一个状态，也可以通过 Context 完成状态迁移。状态类适合每个状态有丰富行为或字段的情况；枚举+转移表适合状态数量稳定、转移规则清晰的情况。

### 代码落点

`behavioral/StateDemo` 用订单的待支付、已支付、已发货、已完成状态展示状态对象委托；同时提供 `EnumStateMachine`，用枚举和转移表集中定义合法流转。

### 优点与代价

优点是状态行为内聚，新增状态不会把所有逻辑塞进一个类，非法流转可以集中拦截。代价是状态多时类数量增加，状态迁移由谁负责也需要明确，否则会出现循环依赖。

### 与策略的区别

策略是客户端主动选择并替换算法，策略之间通常没有转移关系；状态是对象内部随事件自动变化，状态之间有明确的生命周期和合法路径。

## 20. 策略模式（Strategy）

### 要解决的问题

同一个业务目标有多种算法或实现方式，而且这些实现会独立变化。例如支付、排序、折扣、压缩、路由。策略模式把算法封装成可替换对象。

### 结构与工作方式

Strategy 定义统一算法接口，ConcreteStrategy 实现具体算法，Context 持有并调用策略。策略可以在构造时注入，也可以通过 `setStrategy()` 在运行期切换。

### 代码落点

`behavioral/StrategyDemo` 用微信、支付宝、信用卡支付策略和 `PaymentContext` 演示运行期切换；还展示 lambda 策略、Comparator 策略和枚举排序策略。

### 优点与代价

优点是消除条件分支，算法可以独立测试和替换，符合开闭原则。代价是客户端需要理解策略差异，策略类过多时需要注册表或工厂；如果算法永远不会变化，简单方法可能更直接。

### 与模板方法的区别

模板方法通过继承固定整体流程，只让子类改变几个步骤；策略通过组合替换算法对象，变化粒度更大，也更符合运行期切换。

## 21. 模板方法模式（Template Method）

### 要解决的问题

多个业务流程整体顺序相同，但部分步骤实现不同。如果每个子类都重复写完整流程，容易出现顺序不一致和重复代码。

### 结构与工作方式

抽象父类定义不可随意改变的流程骨架，通常用 `final` 方法固定顺序；子类实现抽象步骤，父类还可以提供钩子方法，让子类选择是否改变某个可选步骤。

```text
烧水 -> 冲泡 -> 倒入杯子 -> [钩子] 添加调料
```

### 代码落点

`behavioral/TemplateMethodDemo` 用 `Beverage.make()` 固定饮品制作流程，咖啡和茶分别实现冲泡、加料等步骤，`PlainTea` 覆写钩子跳过配料。

`OnlineOrderSystemDemo.OrderProcessor` 也固定“创建→订阅→校验→支付→发货”流程，秒杀处理器通过钩子增加限购校验。

### 优点与代价

优点是流程一致性强，公共逻辑集中，子类只关注变化步骤。代价是继承带来耦合，父类修改骨架会影响所有子类；步骤变化很多或需要运行期替换时，策略组合通常更合适。

### Spring/JDK 中的应用

`JdbcTemplate` 把获取连接、执行回调、异常转换和资源释放等流程固定下来，只让调用方提供 SQL 或回调；测试框架的生命周期钩子也有模板方法特点。

## 22. 访问者模式（Visitor）

### 要解决的问题

对象结构相对稳定，但经常需要增加不同操作。例如形状集合需要计算面积、输出描述、导出 JSON、生成报表。若把所有操作都放入元素类，元素会越来越臃肿。

### 结构与工作方式

元素提供 `accept(visitor)`，访问者为每种元素类型提供重载的 `visit()`。元素调用 `visitor.visit(this)`，由元素运行时类型和访问者重载共同决定具体操作，这就是双分派。

### 代码落点

`behavioral/VisitorDemo` 中 `Circle`、`Rectangle`、`Triangle` 是元素，`AreaVisitor` 计算面积，`InfoVisitor` 生成描述。增加一个新访问者不需要修改形状类。

### 优点与代价

优点是把许多操作集中到独立访问者中，新增操作方便，元素结构保持稳定。代价是新增元素类型困难：所有访问者接口都要增加一个 `visit(NewElement)`；访问者也可能需要访问元素的内部数据。

### 适用边界

元素类型稳定、操作类型经常增加时适合访问者，例如编译器 AST、报表、静态分析。元素类型经常增加而操作很少时，普通多态通常更简单。

## 23. 解释器模式（Interpreter）

### 要解决的问题

系统需要解释一种简单语言、表达式或规则。与其在一个大方法中解析所有字符串，不如把语法规则表示成对象，并对对象树进行解释。

### 结构与工作方式

- 抽象表达式：定义 `interpret()`。
- 终结符表达式：不可再分的元素，如数字、变量。
- 非终结符表达式：由其他表达式组成，如加法、减法、乘法。
- 上下文：保存变量、输入文本或解析位置。

解释器通常使用组合模式构建抽象语法树。手工组装适合演示和简单规则；实际输入通常还需要词法分析、语法解析、错误定位和优先级处理。

### 代码落点

`behavioral/InterpreterDemo` 中 `NumberExpr` 是终结符，`AddExpr`、`SubtractExpr`、`MultiplyExpr` 是非终结符；`ExpressionParser` 使用递归下降解析器实现乘法优先、加减从左到右。

### 优点与代价

优点是语法规则可组合、扩展新表达式方便、结构直观。代价是每条语法规则可能对应一个类，复杂语法会导致类爆炸和性能问题；复杂语言更适合使用专门解析器或现成 DSL 引擎。

### 工业应用

正则表达式、Spring SpEL、规则引擎、SQL 解析器和编译器 AST 都体现解释器思想。它们通常不会直接使用本示例这么简单的类，而是配合词法分析、AST 优化和执行器。

# 四、如何选择模式

## 按问题分类

| 主要问题 | 优先考虑 |
|---|---|
| 参数多、对象构造步骤复杂 | 建造者 |
| 产品类型变化，需要隔离 `new` | 工厂方法 |
| 多个产品必须成套 | 抽象工厂 |
| 复制已有复杂对象 | 原型 |
| 全局只能有一个实例 | 单例 |
| 接口不兼容 | 适配器 |
| 两个维度独立变化 | 桥接 |
| 文件/菜单等树形结构 | 组合 |
| 动态叠加功能 | 装饰器 |
| 简化多个子系统调用 | 外观 |
| 大量重复对象共享 | 享元 |
| 权限、延迟、远程或日志拦截 | 代理 |
| 请求要沿多个处理者传递 | 责任链 |
| 操作要排队、记录、撤销 | 命令 |
| 隐藏集合遍历细节 | 迭代器 |
| 多个对象之间复杂协作 | 中介者 |
| 保存和恢复对象状态 | 备忘录 |
| 状态变化通知多个订阅者 | 观察者 |
| 对象内部有状态流转 | 状态 |
| 多种算法可替换 | 策略 |
| 流程固定但步骤可变 | 模板方法 |
| 对稳定对象结构增加很多操作 | 访问者 |
| 需要解释表达式或规则语言 | 解释器 |

## 学习顺序

1. 先掌握单一职责、开闭原则、依赖倒置和组合优于继承。
2. 创建型先学建造者、工厂方法，再理解抽象工厂、原型和单例的边界。
3. 结构型按“接口转换 → 组合解耦 → 动态包装 → 访问控制”学习：适配器、桥接、组合、装饰器、代理、外观、享元。
4. 行为型先学策略、模板方法、观察者、责任链，再学习命令、备忘录、状态、中介者、访问者和解释器。
5. 最后阅读 `practice` 和 `springai`，观察多个模式如何组合，而不是把模式孤立使用。

## 复习每个模式时的五个问题

1. 它替调用方隔离了哪一种变化？
2. 哪个对象拥有变化点，哪个对象只依赖抽象？
3. 如果不用这个模式，代码会出现什么重复或耦合？
4. 引入后增加了哪些类、间接调用和调试成本？
5. 这个模式与最相似的另一个模式，判别标准是什么？
